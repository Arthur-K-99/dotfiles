# Roadmap

The goal: one terminal experience that looks and behaves the same on macOS, Debian/Ubuntu/WSL and native Windows. Catppuccin Macchiato everywhere, fast shells, strong autocomplete, and every tool declared in this repository so a new machine is one command away.

Work lands in phases. Each phase is one pull request that leaves every platform in a working state, passes `bash scripts/test.sh` and the Fresh install workflow (`bash tests/fresh_install.sh` locally), and extends `doctor` so a rebuilt machine proves the phase is installed.

Whatever a change uncovers and leaves open is written down here in the same pull request: work to do under "Repository structure", behaviour that is not understood or comes from upstream under "Known issues", and ideas decided against under "Ideas parked". Nothing stays only in a conversation, a pull request description or a commit message.

## Adding a tool: the checklist

Every new tool touches the same places. Skipping one means `doctor` lies on the next machine.

1. Package entries in `packages/brew.txt`, `packages/apt.txt` and `packages/winget.txt`. If a platform has no package, add an installer to `scripts/bootstrap_tools.sh` that is safe to rerun and returns a nonzero status on failure.
2. Configuration under `config/<tool>/`, linked by `scripts/link_dotfiles.sh` and, when the tool exists on Windows, by `Get-DotfilesManagedFiles` in `scripts/lib/windows.ps1`. Destinations derive from the home directory so the tests stay isolated.
3. A `doctor` check in `scripts/doctor.sh` (and `Invoke-DotfilesDoctor` on Windows) for the command, the link and any theme or plugin the tool needs.
4. A test in `tests/unix.Tests.sh` for any bootstrap logic: the already-installed path, a failure, and the retry.
5. A line in the README's "What gets installed" table, its keys in the README's "Key bindings" table, and, if there is anything to know after install, a section in `docs/tools.md` (or `docs/linux.md` and `docs/windows.md` for what differs by platform). Messages it prints that read as errors belong in `docs/troubleshooting.md`.

## Phase 1: Foundations (done)

- One Catppuccin flavor (Macchiato) across tmux, oh-my-posh, eza, fzf and bat.
- tmux: `tmux-256color` for italics, forced RGB, no automatic renaming, renumbered windows, focus events, 50k scrollback, splits in the current path.
- zsh: nvm's default Node on `PATH` without loading nvm (startup 470 ms to 120 ms), fzf keybindings and previews, colored completion menus, larger history, `Ctrl-X Ctrl-E`.
- bat configuration shared across platforms; bootstrap installs the theme for old distribution packages.
- Prompt: git status, execution time, exit status, transient prompt.

## Phase 2: Emulators and PowerShell parity (done)

The emulator is the outermost layer; with it managed, every ANSI-based tool inherits Catppuccin on every platform.

- **Ghostty** (macOS and Linux): `config/ghostty/config`, linked to `~/.config/ghostty/config`, installed by the `ghostty` cask on macOS and by hand on Linux. The theme follows the OS appearance (`theme = light:Catppuccin Latte,dark:Catppuccin Macchiato`; Ghostty wants the names as `+list-themes` prints them, not dashed), CaskaydiaCove Nerd Font Mono, bar cursor, padding, opacity and blur, titlebar tabs, left Option as Alt, Shift+Enter as a newline, and the global quick-terminal hotkey. Ghostty's default keybinds already cover splits and tabs. Cursor shaders and other machine-local settings go in an optional `~/.config/ghostty/local` loaded by `config-file = ?local`. `scripts/test.sh` runs `ghostty +validate-config` on the file wherever Ghostty is installed.
- **Windows Terminal**: a JSON fragment, `config/windows-terminal/fragment.json`, managed into `%LOCALAPPDATA%\Microsoft\Windows Terminal\Fragments\dotfiles\`. Evaluation result: fragments add color schemes and modify the stock profiles (PowerShell 7, Windows PowerShell, Command Prompt) without rewriting `settings.json`, but cannot set global settings such as the default profile or touch WSL profiles, whose GUIDs are derived per distribution. Those two remain a one-time manual setting documented in the README; owning the whole `settings.json` was not worth losing the user's own edits.
- **PSReadLine**: history predictions in the list view plus CompletionPredictor on PowerShell 7, Catppuccin Macchiato colors written directly as hex (no dependency on the `catppuccin/powershell` module, which is not on the Gallery), zsh-like keys (Tab menu, prefix history search, Ctrl+D, Ctrl+W) and `Ctrl+R`/`Ctrl+T` through PSFzf. Everything degrades by feature detection so the same profile loads in Windows PowerShell 5.1 and in non-interactive shells.
- **PowerShell modules**: `Terminal-Icons`, `PSFzf`, `posh-git`, `CompletionPredictor`, installed for PowerShell 7 by a new `install.ps1` stage that runs `pwsh -NoProfile`, verified by `doctor.ps1`, with tests for the installed, failed and retried paths.
- **eza on Windows** (`eza-community.eza`) with the zsh aliases and the shared `theme.yml` through `EZA_CONFIG_DIR`.
- Decision: Ghostty on macOS/Linux and Windows Terminal on Windows. One WezTerm Lua file for three OSes did not outweigh Ghostty's speed and native feel, and the fragment keeps the Windows side small.

## Phase 3: New tools (done)

Autocomplete and shell quality of life on all three platforms, with the exceptions noted.

- **carapace** is the completion engine in zsh and PowerShell. In zsh it is sourced after `compinit` because its script calls `compdef`; fzf-tab keeps drawing the menu. **inshellisense** was evaluated and parked: it is a pty wrapper around the shell with open issues against zsh plugins and tmux, so it would compete with the rest of this setup. carapace can bridge its specs (`CARAPACE_BRIDGES`) if they are ever wanted.
- **atuin** replaces fzf's `Ctrl+R` in zsh (initialised after fzf so its binding wins; `Up` stays zsh's) and in PowerShell 7, where PSFzf then keeps only `Ctrl+T`. PowerShell support shipped in atuin 18.11.0 and is tier-2 upstream; winget installs a current build. Configuration and the vendored Catppuccin theme live in `config/atuin/`.
- **mise** replaces nvm: `config/mise/config.toml` pins Node.js LTS, the bootstrap runs `mise install`, and the doctor checks `mise which node` so a system Node cannot hide a missing one. The lazy-nvm block, the nvm bootstrap, `NVM_DIR` and their tests are gone. Windows gained a runtimes stage for the same `mise install`. In zsh the shims directory goes on `PATH` instead of `mise activate`: the activation hook cost about 115 ms per shell and 20 ms per prompt, while shims resolve the project version when a command runs.
- **git** moved to `config/git/` (XDG `config`, global `ignore`, the vendored `catppuccin/delta` include). Identity and credential helpers stay in `~/.gitconfig`, which git reads afterwards. delta, lazygit and lazydocker are installed everywhere; lazygit reads one path on every OS through `XDG_CONFIG_HOME` on Unix and `LG_CONFIG_FILE` on Windows.
- **yazi** with the Catppuccin Macchiato and Latte flavors. The flavors are packages that `ya pkg add` clones into `~/.config/yazi/flavors`, so only `yazi.toml` and `theme.toml` are linked; the bootstrap adds the flavors or restores them from `package.toml`. `y` changes directory on exit in both shells.
- **vivid** generates `LS_COLORS` for completion menus and fd on Unix. eza keeps its own `theme.yml`, which `LS_COLORS` would override, so an `eza` wrapper blanks the variable for that one command. Not installed on Windows, where nothing but eza reads `LS_COLORS`. Debian 12 ships vivid 0.8 without the Catppuccin themes; the shell checks for empty output and keeps the ANSI default there.
- **Modern CLI set**: ripgrep, fd, dust, duf, procs, sd, xh, hyperfine, glow, tlrc, gum. fd is the fzf backend. **tokei** was dropped: upstream has published no binaries since 12.1.2.
- **zsh extras**: zsh-abbr with a tracked abbreviation file (the `config/zsh-abbr` directory is linked, because zsh-abbr rewrites the file with `mv`, which would replace a file symlink) and zsh-you-should-use; direnv on every platform. **pay-respects** was parked: no Homebrew core formula, no apt or winget package, and the installer wants to edit shell files.
- **Startup time**: with every tool present an interactive zsh took about 320 ms, against 120 ms after phase 1. The init scripts of fzf, carapace, atuin, zoxide and direnv are now cached under `~/.cache/dotfiles/` and regenerated when the binary changes, and mise runs no hook, which brings a warm start to about 230 ms. What remains is oh-my-posh (about 75 ms across init and the first prompt), Homebrew's `shellenv` (25 ms) and zsh-abbr's initialisation (20 ms).
- **Linux installs** gained two generic helpers in `scripts/bootstrap_tools.sh`: `install_apt_repository` for signed third-party repositories (eza, charm) and `install_github_release` for static binaries from the latest release, with the per-project architecture spellings handled by template placeholders. atuin and yazi use their musl builds: the glibc builds need glibc 2.39, newer than Debian 12 and Ubuntu 22.04 provide. Both are tested with mocked network calls.

## Phase 4: tmux, theme switcher, fastfetch (done)

- **tmux moved** to `config/tmux/tmux.conf`, linked to `~/.config/tmux/tmux.conf`. tmux loads that file *and* `~/.tmux.conf` when both exist, so the linker retires the old link and the doctor reports anything left at the old path. TPM and the plugins live under `~/.config/tmux/plugins/`, the directory TPM itself chooses for an XDG configuration; the bootstrap clones TPM there and installs the plugins through a private server as before.
- **Plugins**, in the order TPM runs them: tmux-sensible, vim-tmux-navigator (`Ctrl+h/j/k/l` across panes and, in phase 5, Neovim splits), tmux-yank (`xsel` joins the apt list; `clip.exe` serves WSL and `pbcopy` macOS), tmux-fzf (`prefix F`), tmux-floax (`` prefix ` ``, mirroring Ghostty's quick terminal; the default `p` would shadow previous-window), `catppuccin/tmux#v2.3.1` (2.3.1 fixes a regression with tmux 3.7+) with the directory, session, cpu, battery and date_time modules, tmux-cpu and tmux-battery for the last two, then tmux-resurrect and tmux-continuum, which must be last because it hooks `status-right`. The theme runs once before the status modules are set and again from TPM; both run lines are guarded so the configuration loads without plugins, which lets `scripts/test.sh` source it into a private server and a test check the declaration order.
- **sesh** rather than tmux-sessionx: one static Go binary (Homebrew core, GitHub release on Linux) with zoxide and fzf, `prefix T` to pick or create a session and `prefix L` for the last one; `detach-on-destroy off` so killing a session switches instead of detaching. sessionx would have added bash, bat and a second fzf popup next to tmux-fzf.
- **`scripts/theme.sh <flavor>`** switches the whole repository. Named settings get the new name; files with hex values get each color replaced by the same-named color from the vendored `config/catppuccin/palette.txt`, in the case each file already uses (a value without letters, such as mocha's surface0, carries no case of its own). `config/catppuccin/flavor` records the result and `--check` verifies it. The bootstrap, the doctor and the tests read the bat theme, the yazi flavors and the fzf background from the configuration files, so a switched repository passes `bash scripts/test.sh` and is ready to commit; a test switches a copy through every flavor and back and expects the original bytes. All four atuin themes are vendored and the themes directory is linked, so only the name changes. Corrected along the way: Catppuccin ships with bat 0.26, not 0.25.
- **fastfetch** on every platform (Homebrew, winget, a GitHub release on Debian 12 and Ubuntu 24.04, which apt only covers from Debian 13 and Ubuntu 25.04). The config is `config/fastfetch/config.jsonc` with Catppuccin hex values, which fastfetch accepts directly, and a module list that avoids the slow detectors. zsh runs it in interactive shells outside tmux; PowerShell in the console host when the start arguments carry no `-Command`, `-File`, `-EncodedCommand` or `-NonInteractive`. `DOTFILES_FASTFETCH=0` turns it off. There is no official Catppuccin port for fastfetch; two submissions are open upstream.

## Phase 5: Neovim (done)

- **Base: a hand-rolled lazy.nvim configuration**, `config/nvim/init.lua` plus `lua/dotfiles/` (options, keymaps, autocommands, the lazy.nvim bootstrap) and one file per plugin under `lua/plugins/`. kickstart.nvim moved to Neovim 0.12's experimental `vim.pack` in 2026 and LazyVim is a distribution of dozens of plugins; neither is small enough to understand. Eleven plugins: catppuccin, nvim-treesitter, nvim-lspconfig, mason.nvim, mason-lspconfig.nvim, fzf-lua with nvim-web-devicons, which-key.nvim, gitsigns.nvim, vim-tmux-navigator, and lazy.nvim itself. No completion plugin: Neovim's own `vim.lsp.completion` triggers as you type. No statusline plugin: 0.12's default shows diagnostics and LSP progress.
- **Reproducible and quiet.** `lazy-lock.json` is committed and lazy.nvim's `install.missing` is off, so a start never reaches the network. `lua/dotfiles/bootstrap.lua` does the installing headless: `plugins()` clones missing plugins at the pinned commits and moves drifted ones back (lazy.nvim's `install` alone would clone branch heads and rewrite the lockfile with them; `restore` alone skips what is not installed, so the lock read at startup is put back between the two), `install()` adds the Tree-sitter parsers and Mason packages from `lua/dotfiles/tools.lua`, and `check()` reports every item, which the bootstrap uses as its offline gate and both doctors parse line by line.
- **Neovim 0.12 is the minimum**: nvim-treesitter's `main` branch, the only one that supports current Neovim, requires it. Debian 12 (0.7), Debian 13 (0.10), Ubuntu 24.04 (0.9) and Ubuntu 26.04 (0.11) are all too old, so `install_neovim_release` unpacks the release tarball whole into `~/.local/opt/nvim` and links `bin/nvim`; `install_github_release` would have kept only the binary without its runtime files. The tree-sitter CLI (0.26.1+, needed to compile parsers) comes from Homebrew (`tree-sitter-cli`), winget (`tree-sitter.tree-sitter-cli`) and, on Linux, the GitHub release zip, whose `x64` spelling added the `{arch_node}` template placeholder; `build-essential` joins the apt list for the C compiler. On Windows the compiler is a manual Visual Studio Build Tools install, so parsers there are reported as skipped, not missing, until it exists.
- **Theme:** `flavour = "auto"` with `background = { light = "latte", dark = "<flavor>" }`, so Neovim follows the terminal background like Ghostty and yazi do; `scripts/theme.sh` rewrites the `dark` line and the round-trip test covers it. Catppuccin's `auto_integrations` themes the installed plugins.
- **Language servers** through Mason: lua_ls, bashls, ts_ls, pyright (npm rather than basedpyright's pip, so Windows needs no Python), jsonls, yamlls, marksman, taplo, powershell_es (enabled only where `pwsh` exists, with Mason's bundle path). Mason runs npm from mise's Node.js, which the bootstrap puts on PATH for that step.
- **Windows:** `Get-DotfilesManagedFiles` enumerates every file of `config/nvim` into `%LOCALAPPDATA%\nvim`, so a new Lua file is managed without editing the list; the runtimes stage runs the same headless install and the doctor the same report.
- **Checks:** `scripts/test.sh` runs `tests/nvim_check.lua` through `nvim -l` (no configuration, no network): every Lua file parses and the plugin specs match the lockfile both ways. The Ubuntu CI job installs Neovim for it. Unix tests cover the Neovim and tree-sitter release installers (installed, too old, download failure, retry, bad archive, old release, file in the way, arm64), the bootstrap step, the doctor, and `plugins()` itself against local git repositories (a failed clone must leave the lockfile untouched); the Windows suite covers the install stage, the doctor's report parsing, the version and Node.js discovery, and pushes the Lua arguments through a real child process, because Windows PowerShell strips inner double quotes from native arguments.

## Repository structure

Not tied to a phase; pick up when convenient.

- Opt-in profiles (`minimal`, `development`, `personal`) as the README already proposes, so GUI apps and OS preferences never change every machine silently.
- A Brewfile so `brew bundle check` reports drift, if the current parsed lists become limiting.
- **Signatures where projects publish them.** Release downloads are checked against GitHub's digest, which comes from the same release, so an asset replaced by someone able to publish there would still pass. Some projects sign their releases, which would close that gap:
  - **oh-my-posh** signs `checksums.txt` with Ed25519 (`checksums.txt.sig`; the public key is in its repository at `src/cli/upgrade/public_key.pem`, where `oh-my-posh upgrade` uses it). `openssl pkeyutl -verify -pubin -rawin` checks it with OpenSSL 3; macOS ships LibreSSL.
  - **mise** signs `SHASUMS256.txt` with minisign (`minisign.pub` at its repository root) and GPG (`24853EC9F655CE80B48E6C3A8B81C9D17413A06D`). Its `self-update`, which the update already uses, checks a signature of its own.
  - **atuin, tlrc, tree-sitter and mise** publish SLSA build provenance. `gh attestation verify --bundle <file> -R <repo>` checks a bundle fetched from the API without a login, but every distribution's gh predates 2.49, which added the command.
  - **Nothing signed** comes from delta, yazi, dust, procs, xh, zoxide, Neovim, fastfetch, the Nerd Fonts, lazygit, lazydocker, carapace-bin or sesh (the last four publish unsigned goreleaser checksums).
  - **Immutable releases** already close the gap where a project turns them on: oh-my-posh's v31.8.0, mise's v2026.10.9 and Homebrew's 7.0.9 are marked `immutable`, so their assets cannot be replaced after publishing, and each carries a GitHub release attestation (`gh release verify-asset`). The API's `immutable` field could be shown, or required, per tool.
- **The release age beyond GitHub releases.** `DOTFILES_MINIMUM_RELEASE_AGE` covers the Unix bootstrap's GitHub release downloads and reaches mise. Everything else takes a release as soon as its channel offers it:
  - the eza and Charm apt repositories, which publish what each project builds (Debian's and Ubuntu's own archives freeze versions per release);
  - Homebrew formulae and casks (Homebrew waits a day only for npm, PyPI and gem versions, when its maintainers bump formulae and when formulae resolve their build dependencies) and winget;
  - zinit's and TPM's plugins and the yazi flavors, at their branch heads;
  - the language servers Mason installs, at their latest versions (Mason has no age setting; its npm packages could get npm's `min-release-age`, in days, from npm 11.10);
  - on Windows, the PowerShell modules from the PowerShell Gallery and the Nerd Font from `oh-my-posh font install`. `install.ps1` reads no age setting; mise there comes from winget, and only its runtime installs wait mise's own default day.
- **Cheaper release lookups.** `github_latest_tag` follows the `releases/latest` redirect with `-L`, so it downloads each release page (200 to 235 KB, about 4 MB per install) and throws it away; `-w '%{redirect_url}'` without `-L` reads the tag from the redirect alone. And while a latest release is too young, every update run asks for it and for the list again (two requests per tool); a note of the held-back tag and its publication time under `~/.local/state/dotfiles/` would let runs skip both until it is old enough.
- **A desktop Windows 11 run.** The Windows fresh install runs on Windows Server 2025, elevated, so some paths are still seen only by the mocked suite:
  - **Links or copies.** The runner always makes links (35 linked, none copied). `docs/windows.md` says links need an elevated shell, or Developer Mode with PowerShell 7, and that Windows PowerShell 5.1, which runs the first install, checks for elevation itself (the installer handles its `NewItemSymbolicLinkElevationRequired` error). A copy that still matches counts as installed, so a rerun after turning on Developer Mode keeps it; `docs/windows.md` says to delete the copies first, and the linker could replace a matching copy with a link whenever one can be made.
  - **The update from inside Windows Terminal and PowerShell 7.** Leaving the running ones alone is a precaution, never tried: the runner upgraded Windows Terminal from outside it and never upgraded a running PowerShell.
  - **The prompt and the start time** (next to-do and Known issues).
- **oh-my-posh on Windows from its release.** winget's oh-my-posh is an MSIX package (`appx` in 31.8.0 on the runner; winget-pkgs offers MSIX beside the MSI from 26.25.0 and only MSIX from 29.30.0), started through an alias in `WindowsApps`. Upstream, [JanDeDobbeleer/oh-my-posh#7833](https://github.com/JanDeDobbeleer/oh-my-posh/issues/7833) reports for 30.8.0, 31.3.0 and 31.5.0 (last on 2026-10-13; closed, and the maintainer cannot reproduce it) that PowerShell cannot start `oh-my-posh.exe` from the prompt ("The file cannot be accessed by the system") and that the App Installer window opens on every prompt. One probe on the runner hit the first part, and on 2026-10-14 the full install on main did too: `oh-my-posh font install`, the first call after winget installed it, failed with that error and stopped the install ([run 38615827813, attempt 1](https://github.com/Arthur-K-99/dotfiles/actions/runs/38615827813/attempts/1); the second attempt passed). That is one of 13 CI installs that reached the font (the other 12 started oh-my-posh), and the 1.0.0 release notes list it as a known limit. Installing `posh-windows-amd64.exe` (or `-arm64.exe`; each has a digest, and the releases are immutable) into `~\.local\bin`, as on Unix, would avoid it, but needs the digest check and the release age in PowerShell.
- **Upstream reports from the Windows fresh install,** worth filing: winget's exact-id lookup of `rsteube.Carapace` (winget-pkgs or winget-cli; see Known issues), CompletionPredictor's deadlock in a non-interactive host that loaded PSReadLine late (PowerShell/CompletionPredictor), and oh-my-posh importing PSReadLine in non-interactive shells for its key handlers.
- **oh-my-posh from Homebrew on macOS.** On macOS oh-my-posh comes from its GitHub release into `~/.local/bin`, while every other macOS tool comes from Homebrew, and homebrew-core carries it (31.8.0 on 2026-10-12). Adding it to `packages/brew.txt` needs care on machines that still have the old `jandedobbeleer/oh-my-posh` tap: its formula of the same name shadows core's, and Homebrew 7 refuses to load it (see Known issues).
- **The Nerd Font on Windows: updates and verification.** One fix covers both: fetching the font from its release the way Linux does. `oh-my-posh font install` now gets the release's `latest/download/CascadiaCode.zip` URL, which spares it GitHub's API, but still nothing checks the archive or records its release.
  - The update keeps the Nerd Font that `oh-my-posh font install` put on Windows, since nothing records which release it was. Linux replaces the font when Nerd Fonts publishes a newer release and it is old enough, and macOS upgrades the cask when Homebrew installed it.
  - `oh-my-posh font install` takes the Nerd Fonts zip from the GitHub release without checking any hash: it ignores the API's digest, only checks that the answer is a zip, and reuses a copy cached in the temporary directory for a day (oh-my-posh v31.8.0, `src/cli/font/`). Every program `install.ps1` installs comes from winget, which compares each installer with the SHA-256 in its manifest; the PowerShell modules come from the PowerShell Gallery.
- **The Homebrew installer.** `scripts/install_packages.sh` runs `install.sh` from `Homebrew/install` at `HEAD`, as Homebrew's instructions say; it has no checksum or signature. On Apple Silicon the signed and notarized `Homebrew.pkg` from Homebrew/brew's latest release is the verifiable alternative; that release is immutable, so `download_release_asset` would check it too. Bottles and casks themselves are checked against the SHA-256 in their formula or cask.
- **Ownership of plain files in `~/.local/bin`.** Any plain file there with a tool's name counts as the bootstrap's, even without a release record (machines installed before records existed have none), so a binary that `cargo install --root ~/.local` or a manual copy put there is replaced by the update. Links are left alone. Refetching only recorded tools would leave older machines un-updated instead.
- **A font opt-out for headless Linux.** Every Linux machine outside WSL now installs fontconfig and the 33 MB Mono family, including servers reached only over SSH, where the client draws the text, and the doctor fails without the font. Headless machines cannot be detected reliably, so a variable like `DOTFILES_FASTFETCH=0` is the likely shape.
- **btop in Catppuccin.** btop is installed everywhere but keeps its default colors, which `docs/theming.md` lists as not yet managed. A theme file would need linking on every platform (btop4win on Windows) and a location in `scripts/theme.sh`.
- **Messages that name relative paths.** The Windows stages' `Rerun install.ps1` and `Rerun scripts\update.ps1` hints read wrong from another directory. The skipped-parser pointer names `docs/troubleshooting.md` only "in the dotfiles repository", with `/` on Windows, because `bootstrap.lua` runs from the copy in `%LOCALAPPDATA%\nvim`.
- **An uninstall command.** `docs/troubleshooting.md` lists by hand what to remove: the links and their backups, the downloaded state, the apt repositories, the packages. The linker's list, the release records and the package lists hold enough for a script to do it, except telling packages the user had before.
- **Ghostty's `ssh-terminfo`, back on once upstream fixes it.** Off because Ghostty 1.3.1 runs a command given to `ssh` twice with it (Done, below).
  - Report it to Ghostty, whose bug reports start as an "Issue Triage" discussion (none found on 2026-10-15): the install connection passes the user's arguments, remote command included, before its own script.
  - `main`'s `+ssh` action (`src/cli/ssh.zig`, which replaces the shell wrappers after 1.3.1, the latest release) does the same and discards the install's stdout, so the command would still run twice, unseen. Its script also has no leading newline, so its first line joins the command's last: `ssh host 'rm -rf build'` would first run `rm -rf build command -v tic >/dev/null 2>&1 || exit 1`. It writes the cache only when the final `ssh` exits 0.
  - Before turning it back on, from a Ghostty shell: delete `/tmp/count` on the host, run `ssh <host> 'echo x >> /tmp/count #'` and check that `/tmp/count` has one line. The `#` keeps an install script appended on the same line, as `main` does, out of the redirection. Check once against a host without `tic`, and once against one with `tic` after `ghostty +ssh-cache --remove=<user>@<hostname>`, as `ghostty +ssh-cache` lists it (`main` adds `:<port>` for a port other than 22).
- **Network calls that `dotfiles_curl` does not bound.** git clones and pulls (zinit, TPM and its plugins, lazy.nvim, `ya pkg` for the yazi flavors) have no stall limit; `GIT_HTTP_LOW_SPEED_LIMIT` and `GIT_HTTP_LOW_SPEED_TIME` would give one. apt, Homebrew, mise, Mason, nvim-treesitter and everything on Windows (winget, the PowerShell Gallery, `oh-my-posh font install`) keep their own tools' timeouts.

Done:

- **Bounded downloads** (2026-10-16; PR link to follow), the roadmap's "Bounded curl failures":
  - **Unreachable hosts and stalls.** No curl call set `--connect-timeout`, so a host that drops packets cost the system's connect limit a try (75 seconds on macOS, about 136 on Debian 12, measured), which curl reports as a timeout and `--retry 7` retried: about 12 minutes on macOS and 20 on Linux per download. Nothing ended a transfer that stopped sending.
  - **The limits.** Every curl download goes through `dotfiles_curl` (`scripts/lib/environment.sh`): `--connect-timeout 30`, `--speed-limit 1 --speed-time 60` (a try averaging under a byte a second for a minute, the wait for the answer included), `--retry 7` and `--retry-max-time 180`. Both limits end a try as a timeout, which is retried, and no retry starts after three minutes, which also caps a server's Retry-After. A download that cannot get through now fails within about 4 minutes, an API request (`--retry-max-time 120`) within about 2. A name that does not resolve is retried too, so an offline machine spends about two minutes per download; only a refused connection fails at once.
  - **macOS retries HTTP/2 errors now.** With `-f`, macOS's curl 8.7.1 exits 56 instead of 22 for an HTTP error over HTTP/2 (reported upstream as a regression of 8.7.x), and `--retry` retries only 22, so on macOS no 5xx was retried. `--fail-with-body` exits 22 there: against a local HTTP/2 server, two 503s were retried to success, where `-f` made one request. The error body lands in the `-o` file, which every caller deletes on failure.
  - **Retries append to stdout.** Checked with a local server on curl 8.7.1 and Debian 12's 7.88.1: after a stall, a retry into `-o <file>` starts the file over, but on stdout it follows what the stalled try wrote (`xxxxxxxxxxok`). The GitHub API request and the Homebrew installer read curl's stdout, so a stall would have spliced a partial script in front of the whole one. Both now download into a temporary file (the API's in the run's cache directory, whose trap removes it).
  - **The token retry.** With `GITHUB_TOKEN` set, `github_api_request` repeated any failed request without it, a 5xx or timeout included, which doubled the wait during an outage and called it a refusal. It now reads the status with `-w '%{http_code}'` and retries only after 401 or 403. Against GitHub: a bogus token got 401 and the retry, a valid one no message, a missing repository (404) one failure.
  - **Tests:** `downloads_are_bounded` checks the options, that no script runs curl or wget but `dotfiles_curl`, and that every call names a file after `-o` (curl run through a variable would escape it); `release_download_verification` adds the 403 retry, and an outage and a silent host with a token, each one request. No test drives the Homebrew installer download itself; the static check covers it.

- **`ssh host cmd` ran `cmd` twice in Ghostty** (found trying 1.0.0 on this Mac, 2026-10-15; [#23](https://github.com/Arthur-K-99/dotfiles/pull/23)):
  - **Symptom:** every `ssh deployer@<host> '<cmd>'` printed `Setting up xterm-ghostty terminfo on <host>...`, the command's output, `Warning: Failed to install terminfo.`, and the output again. The host is an OrbStack Rocky Linux machine; Ghostty hides why the install failed (no `tic` is the likely cause).
  - **Cause:** `shell-integration-features` turned on `ssh-terminfo`. Ghostty 1.3.1's zsh `ssh` wrapper then installs its terminfo entry over a first connection that gets all of `ssh`'s arguments plus its install script. ssh joins them into one command line and the script starts on a new line, so the user's command runs first, with its stdout shown and the terminfo text as its stdin. The wrapper always ends with a second `ssh` carrying the command. A successful install is cached, so only the first call to that host runs the command twice; a failed one is not, so every call does.
  - **Fix:** `ssh-terminfo` is off; `ssh-env` still sends `TERM=xterm-256color`, and `COLORTERM` where the host accepts it. Ghostty's own wrapper, sourced with a stand-in `ssh` that simulates a host without `tic` and counts the runs, ran the command twice with the old features and once with the new ones. Hosts already in Ghostty's cache now get `xterm-256color` too (none on this Mac).
  - **Left behind:** each install attempt left an empty `/tmp/ghostty-ssh-<user>.XXXXXX` directory, which can be deleted by hand.

    - an nvm alias there (`node`, `stable`) is a version mise cannot resolve (`mise install --dry-run` planned `node@node`), so the bootstrap's `mise install` would likely fail;
    - a `package.json` `devEngines.runtime` would choose Node.js too.

    The README now says how to opt in (`MISE_IDIOMATIC_VERSION_FILE_ENABLE_TOOLS=node` in `~/.zshrc.local`) and what follows.
  - **`DOTFILES_LOCAL_BIN` reaches the shell.** `~/.zshrc` put `~/.local/bin` on `PATH` whatever the installer used. It now puts the variable's directory first when it is set (exported from `~/.zshenv`, since `~/.zshrc.local` loads after `PATH` is built) and keeps `~/.local/bin`, where pipx, uv and npm link their tools.
  - **A stale comment:** Ghostty's config named `.tmux.conf` for the tmux configuration.
  - **The tests clear `DOTFILES_LOCAL_BIN`,** as they do the other settings: exported from `~/.zshenv`, as the README now suggests, it made `environment_discovery` fail.

- **A minimum release age** ([#15](https://github.com/Arthur-K-99/dotfiles/pull/15)). mise.run installed the newest mise release at least a day old and `mise self-update` waits a day, while every other release tool took a release minutes after it was published. Now every GitHub release download of the Unix bootstrap waits.
  - **The setting.** `DOTFILES_MINIMUM_RELEASE_AGE` is a whole number of at most nine digits with a unit, `s`, `m`, `h`, `d` or `w` (the grammar of mise's installer, `^[0-9]+[smhdw]$`), plus a bare `0` for off. It is a day when unset or empty. `install.sh`, `scripts/update.sh` and the bootstrap stop before their first stage on anything else.
  - **Which release** (`release_tag` in `scripts/bootstrap_tools.sh`), for the release tools, oh-my-posh, zoxide, mise's first install, Neovim, the tree-sitter CLI and the Linux font, on a first install and in the update:
    - **The latest release once it is old enough.** "Latest" stays what the `releases/latest` redirect names: the release the project marks so.
    - **While it is younger, the highest version that qualifies** among the 30 most recent releases. It must be old enough, no higher than the latest, and carry the asset with a SHA-256 digest. Drafts, prereleases and tags that are not plain version numbers never count: Neovim's `stable`, every `nightly`, and prereleases their projects did not flag (tree-sitter's `v0.21.0-pre-release-1`, dust's `v0.8.1-alpha.1`).
    - **The installed release when it is at least as new.** The update moves on once a newer release is old enough.
    - **Never an older release than the recorded one,** whatever the setting. A project, or someone with its rights, deleting its newest releases makes "latest" go back, and that would otherwise roll machines back. Neovim and the tree-sitter CLI fall back on the version they run when nothing is recorded; the other release tools and the font, installed before records existed, are not protected on their first update.
    - **No release old enough:** a tool that is not installed yet stops the run (on a first install, or a tool the update adds), saying how to override; the update keeps what is installed.
  - **A release's age** is the later of its `published_at` and the newest `updated_at` among its assets. A release's `created_at` is its tag's date (the commit's, or the tagger's), months before publishing at times; its own `updated_at` moves whenever the notes are edited. A file replaced after publishing makes the release that young again.
  - **The API cost.**
    - One request per download, as before, when the latest release is old enough: each run keeps every API answer in a temporary directory, so the age check and the digest check share the release's.
    - One more, the list, for each release held back, which also serves the older release's digest.
    - API answers are now requested compressed: a page of 30 releases runs to megabytes.
    - Measured anonymously with the `rate_limit` endpoint (which costs nothing) on 2026-10-14, a Debian 12 fresh install with its rerun and update took 37 requests: 18 downloads plus a list each for mise and fastfetch, whose latest releases were younger than a day (fastfetch's 2.70.0 came out 40 minutes before the run), none for the rerun, and 16 downloads plus fastfetch's list for the update. Before this change it took 35. An earlier draft spent two requests per held-back release (a Debian 13 run took 37 with mise alone held back).
    - A Debian 12 tree-sitter that does not run on its glibc made a plain rerun read the latest release's age every time in that draft; the release left out now counts as installed for `release_tag`, so a rerun asks only for the latest tag, as before.
  - **mise,** when `DOTFILES_MINIMUM_RELEASE_AGE` is set, gets it as its own `MISE_MINIMUM_RELEASE_AGE` (in seconds, such as `86400s`), unless that is already in the environment. Its self-update and its runtime installs honour it ahead of a `minimum_release_age` in mise's configuration, but behind `MISE_SELF_UPDATE_MINIMUM_RELEASE_AGE` and `self_update.minimum_release_age` for the self-update. Unset, mise waits its own default day. A fresh install's update showed `Selected mise 2026.10.8 (minimum release age: 86400s)`.
  - **The doctor says nothing about release ages.** It checks what is installed, offline, and a release held back is a correct install. The installers already reject a bad setting before anything changes and print every release they pass over.

  **Found along the way:**
  - **How others do it.**
    - **mise:**
      - `mise.run` picks the highest version from `https://mise.jdx.dev/releases.tsv` (tag and `published_at`, written on each release with no delay of its own) published before `MISE_SELF_UPDATE_MINIMUM_RELEASE_AGE`, `MISE_MINIMUM_RELEASE_AGE` or 24h. It keeps a newer installed binary and fails when nothing qualifies.
      - `mise self-update` does the same, never downgrades, and also requires the release's transparency-log time to be old enough.
      - mise's tool installs have the same setting (24h by default since v2026.6.2), measured from `published_at` since mise found that `created_at` let fresh releases through.
    - **Elsewhere:** pnpm `minimumReleaseAge` (minutes, 1440 by default since v11), npm `min-release-age` (days, since 11.10), uv `exclude-newer` (dates or durations), Renovate `minimumReleaseAge`, Dependabot's cooldown (3 days by default since 2026-07), bun and yarn.
    - **What they do when the newest is too young:** every one takes the newest version that qualifies rather than waiting. mise never downgrades, and Renovate proposes no rollback unless told to (`rollbackPrs`).
  - **Why take an older release rather than wait.** The 100 most recent releases of the 18 projects, replayed hour by hour over the past year (mise's 100 reach back only to April 2026, oh-my-posh's to December 2025):
    - At least one tool's latest release was younger than a day in 58% of hours (89% at 3 days, 96% at 7). mise's latest alone was younger than a day in about 22 to 24% of hours, and so was oh-my-posh's; mise releases about every 1.7 days, oh-my-posh about every 3.
    - Waiting for the latest to age would have stalled mise's updates for up to 4, 23 or 104 days in a row (1, 3 or 7 days' delay), and oh-my-posh's for up to 5, 22 or 71.
  - **What a day would have caught.** The bad versions of Trivy v0.69.4 (a GitHub release with backdoored binaries, about 3 hours in 2026-03), axios on npm (about 3 hours), Nx "s1ngularity" (4 to 5 hours), chalk/debug (about 2 hours) and Ultralytics on PyPI (1 to 12 hours) were all pulled within a day. Amazon Q's 1.84.0 stayed up for about 31 hours, and xz's tarballs for weeks; GitHub's own review of 21 incidents ([The case for a cooldown](https://github.blog/security/supply-chain-security/the-case-for-a-cooldown-why-dependabot-now-waits-before-issuing-version-updates/)) found most bad versions "pulled within hours".
  - **Releases that are not what they seem:**
    - **Late uploads:** 8 of the 18 latest releases had assets uploaded after publishing (carapace's 18 minutes later), and Nerd Fonts replaced v3.4.0's assets a month after publishing it (and v3.0.2's seven weeks after).
    - **Moving prereleases:** yazi's `nightly` keeps a 2024 `published_at` while its assets are replaced daily; Neovim and tree-sitter recreate theirs daily.
    - **Duplicates:** Neovim publishes a non-prerelease `stable` beside every version.
    - **Releases without builds:** carapace v1.7.2, sesh v2.30.0 and three mise releases carry no assets, and fastfetch 2.66.1, a bugfix of an older line without binaries, sits above 2.67.x in the list.
  - **API facts:**
    - The list is ordered by tag date, not by publication.
    - "Latest" is the project's `make_latest` flag, not the newest release.
    - A page costs one request whatever `per_page` is. At a day's delay ten releases always sufficed over the past year, but atuin's betas fill five, and at seven days oh-my-posh needed fourteen, hence 30.
    - A `304` from a conditional request counts against the anonymous limit; only authenticated ones are free.
    - `releases.atom` lists plain tags as well as releases, has no prerelease flag, and dates entries by their last edit, so it cannot replace the API.
    - `browser_download_url` percent-encodes the tag (k3s's `v1.37.1+k3s1` becomes `v1.37.1%2Bk3s1`), so assets are keyed by `tag_name` and the asset's `name`.
  - **A review pass** (two agents) compared both parsers with Python's JSON parser on 1,336 real releases and 27,033 assets, minified and pretty-printed, under UTF-8 and C locales; ran the tests under macOS's bash 3.2, Debian 12 (mawk and gawk) and Ubuntu 26.04 (uutils); and checked `curl --compressed` there (all three curls have zlib). It found, and this PR fixes:
    - suffixed tags (`-pre-release-1`, `-alpha.1`, `-rc.1`) counted as their version, so an unflagged prerelease could be taken and then kept as "newer" than the final release;
    - the extra requests on Debian 12 reruns above;
    - percent-encoded tags missing their digest;
    - an update without a record moving Neovim or the tree-sitter CLI to an older release while the latest was young;
    - messages that named the wrong asset or called an asset's upload time a publication;
    - the mise hand-off overriding mise's own configuration even when `DOTFILES_MINIMUM_RELEASE_AGE` was not set, and docs that stated mise's precedence wrongly;
    - several sentences in the README and comments that still said "the latest release".

    It also added a test of `bootstrap_tools_main`'s cache directory. Left open: a tool with a missing binary whose sibling from the same release is installed is fetched again at its recorded tag, and fails when the project has deleted that release since.

- **apt keyrings kept current and checked** ([#14](https://github.com/Arthur-K-99/dotfiles/pull/14)). [#13](https://github.com/Arthur-K-99/dotfiles/pull/13) pinned the repository keys but fetched one only while a package of its repository was missing, so a keyring a machine got before the pins was never checked, and an expiry the project extends would never reach it.
  - **A shared table.** The repositories, their key URLs, pins and sources lines live in `scripts/lib/apt_repositories.sh`, which the package stage, the bootstrap and the doctor all read.
  - **The update fetches the keys again.** The fetch runs before the package stage's `apt-get update`, for each repository whose sources list the bootstrap wrote. A key that no longer matches its pin stops the update. A key that cannot be downloaded (an outage, a proxy) leaves the keyring as it is, with a warning, since the keyring is still what it was and the doctor checks it. Otherwise:
    - **The keyring holds the pinned key:** the download is merged into it with gpg (both imported into a throwaway home, then exported with default options), so an extended key keeps its old self-signature beside the new one. When the merge adds nothing, the keyring is left alone.
    - **It holds any other key** (one from before the pins): it is replaced.
    - **There is none yet:** it is installed.
    - **In every case** the result is installed with `sudo install -m 644` into a directory made with mode 755, and gpgconf stops the agents gpg starts in the throwaway homes and removes their socket directories.
    - **Without gnupg** the refresh waits for the next update, since the package stage reinstalls it from `packages/apt.txt`.
  - **The doctor checks each keyring.** It must be readable (apt reads it as `_apt`), hold exactly the pinned key, and that key must not have expired. A key that expires within 30 days passes, with its date shown. Each keyring's expiry comes from `gpg --show-keys` (field 7 of the `pub` record). Only the primary key's expiry is read, which signs each repository's `InRelease`; a project that moved its signing to a subkey would need the subkey's.

  **Found along the way:**
  - **apt-get update with an expired key.** Tested in containers with a key that expired in 2020:
    - **Fresh lists, gpgv** (Debian 12, Ubuntu 24.04 and 26.04): exit 100, `EXPKEYSIG` and "The repository ... is not signed".
    - **Fresh lists, Debian 13:** apt verifies with Sequoia's sqv, which judges a signature by the key's validity when the signature was made. An index signed before the expiry still passes; one signed after fails.
    - **Earlier lists:** wherever lists from a good update exist, every distribution only warns ("The repository is not updated and the previous index files will be used") and exits 0. A provisioned machine whose key expires therefore keeps its old lists and exits 0, so nothing fails.
    - **No advance warning:** none of the four distributions warns about a key that expires in a few days, hence the doctor's 30-day notice.
  - **Replacing the keyring with an extended key breaks Debian 13 for a while.** `gpg --quick-set-expire` replaces the self-signature, so a key extended that way carries only the new one. sqv then finds no binding valid when the old index was signed and refuses it until the project signs the index again; gpgv uses the newest self-signature and accepts both indexes.
    - **Merging fixes it.** Importing both copies and exporting them keeps both self-signatures; the merged keyring verified the old index, the new one, and an update from old lists to the new index on all four distributions.
    - **Export options:** `export-minimal` and `export-clean` drop the old self-signature.
    - **Concatenation does not work:** `cat old new` fails under gpgv, which reads only the first copy of a key, and `--show-keys` lists such a file's fingerprint twice.
  - **A review pass** (two agents) tested the merge with real signed repositories on all four distributions, keyboxd homes, keyrings written by the old `gpg --dearmor` bootstrap (reported current, no sudo), and users without a writable home. It found:
    - **Socket paths too long for macOS CI.** Without `/run/user/<uid>` (macOS, containers, su, cron), gpg puts its agent's sockets in the home, and a socket path is limited to about 104 bytes. The macOS runner's long TMPDIR would have made the tests' key generation and the import fail with gpg 2.5.22. The throwaway homes now live under `/tmp`.
    - **Silent import failures.** `--quiet` already keeps a good import silent, so the `2>/dev/null` only hid errors; they are now shown.
    - **Download failures.** A failed key download stopped every update, which now keeps the keyring as described above.
    - **Leftover socket directories:** one per throwaway home under `/run/user/<uid>/gnupg`; `gpgconf --remove-socketdir` takes them away.
    - **Doctor wording:** an unreadable keyring was reported as missing.
    - **Directory mode:** `sudo mkdir -p /etc/apt/keyrings` under umask 077 would make the directory unreadable to `_apt`.
    - **Docs:** the notes overstated when `apt-get update` fails.
  - **Debian 13 rejects SHA-1 self-signatures** since 2026-02-01 (sqv as apt runs it). Charm's self-signatures are SHA-256 and eza's SHA-512.
  - **What signs the indexes.** Charm's primary key signs its `InRelease`; its subkey only encrypts, so the primary key's expiry is the one that matters. Gemfury serves Charm's index, last signed on 2026-10-09. eza's key never expires.

- **Verified downloads** ([#13](https://github.com/Arthur-K-99/dotfiles/pull/13)). The files the Unix bootstrap downloads with curl, except Homebrew's installer, are checked or pinned before they are used. Plugins still come from git as before (Neovim's pinned by `lazy-lock.json`).
  - **GitHub releases.** Each download is checked against the SHA-256 digest GitHub lists for the asset in its releases API (`download_release_asset`). This covers the release tools, Neovim, the tree-sitter CLI and the Linux font. A file that does not match is deleted before anything is unpacked or replaced. Each download costs one API request, parsed without jq: the JSON is split at commas, brackets and braces, which works on both the pretty-printed answer curl gets and the minified one other clients get.
  - **Installer scripts.** oh-my-posh (macOS and Linux), zoxide and mise no longer come from installer scripts piped into a shell. They are release downloads like the rest: `posh-{os}-{arch_deb}`, zoxide's musl tarball and mise's musl binary. The release records the scripts wrote stay valid, so the first update fetches oh-my-posh and zoxide again only when a newer release exists; mise keeps updating itself.
  - **apt repositories.** eza's and Charm's are added only when the downloaded signing key has the fingerprint pinned in `scripts/bootstrap_tools.sh` (since moved to `scripts/lib/apt_repositories.sh`). The key is read with `gpg --show-keys` in an empty, temporary GNUPGHOME, since gpg would otherwise create `~/.gnupg` (or fail where the home is not writable).
  - **bat themes.** The Catppuccin themes come from a fixed commit of catppuccin/bat instead of `main`.
  - **Tokens.** `GITHUB_TOKEN` raises the API limit and goes to curl on stdin. GitHub answers a token it does not accept (expired, or meant for another host) with 401 instead of answering anonymously, so a failed request is made once more without it. The Fresh install workflow passes the job's token, and `tests/fresh_install.sh` passes it into the container.
  - **Errors.** An asset missing from its release (renamed upstream, or not uploaded yet) is reported as such, apart from an asset without a SHA-256 digest.

  **Found along the way:**
  - **Checksum files.** About half the projects publish their own: lazygit, lazydocker, carapace-bin and sesh (goreleaser `checksums.txt`), atuin (`.sha256` per asset and `sha256.sum`), Nerd Fonts (`SHA-256.txt`), oh-my-posh (`checksums.txt` with an Ed25519 signature) and mise (`SHASUMS256.txt`, signed with minisign and GPG). delta, yazi, dust, procs, xh, tlrc, fastfetch, Neovim, tree-sitter and zoxide publish none. GitHub's digest covers all of them.
  - **Digests appeared on 2025-06-03 and were not backfilled.** Every asset uploaded earlier has `"digest": null`: for example fzf before v0.63.0, bat before v0.26.0, zoxide before v0.9.9 and delta before 0.19.0. The current release of every tool here has digests. A tool whose latest release predates June 2025 would be refused with a message saying so.
  - **What the installer scripts did.**
    - **oh-my-posh:** downloaded from its own CDN (`cdn.ohmyposh.dev`) and checked nothing. It ran the unchecked binary, always unpacked the latest `themes.zip` into its cache (even when given a version), and made the themes world-writable (`chmod a+rwX`).
    - **zoxide:** checked nothing either. It copied man pages into `~/.local/share/man/man1`; the release download leaves them out, as it does for every release tool, and pages an earlier install copied stay where they are.
    - **mise.run:** checked SHA-256 against hashes embedded in the script, or against the release's `SHASUMS256.txt` without checking its signature. It installed the newest release at least a day old, which the first install stopped doing until the minimum release age (above) brought it back for every GitHub release download.
  - **Neither apt key's fingerprint is published by its project.** Not by eza's INSTALL.md, not by Charm's READMEs, and not on keys.openpgp.org. The pins are the keys that sign each repository's `InRelease`, checked with `gpgv`. Charm's key is also on keyserver.ubuntu.com and identical to its yum key.
  - **A review pass** (two agents) checked the parser against all 501 assets of the 18 current releases, compared with a real JSON parser, under macOS's bash 3.2 and BSD tools, Debian 12 and Ubuntu 26.04 (mawk and uutils `tr`). It found the token, missing-asset and SIGPIPE problems fixed above (awk no longer exits at the match, which printed "Broken pipe" where SIGPIPE is ignored), several overstatements in these notes, and test assertions written as `a && b`, of which errexit only enforces the last; those were split.
  - **The API pretty-prints for some clients only.** It indents JSON for a curl or Wget User-Agent and sends one line to others, whatever the Accept header. GitHub answers a token it does not accept with 401 rather than falling back to anonymous access, and an exhausted limit with 403 or 429. curl retries a 429 and honours any Retry-After, however long; with `--retry-max-time 120` on the API call, a longer Retry-After makes curl give up at once instead.

- **An update command** ([#12](https://github.com/Arthur-K-99/dotfiles/pull/12)). `scripts/update.sh` and `scripts/update.ps1` run the install stages again with `DOTFILES_UPDATE=1` (Windows: `-Update`). Besides adding what is missing, they upgrade:
  - **Packages:** only the ones `packages/*.txt` declares.
  - **Release tools:** each tool fetched from a GitHub release or installer script is fetched again when the latest tag differs from the one recorded under `~/.local/state/dotfiles/releases/<owner>/<repo>`.
  - **Plugin managers:** zinit, TPM and their plugins.
  - **Runtimes and flavors:** mise's runtimes (`mise upgrade`, run from the home directory) and the yazi flavors.
  - **Neovim:** `require("dotfiles.bootstrap").update()` brings the parsers to the revisions the pinned nvim-treesitter names and the Mason packages to their latest versions. The plugins stay on `lazy-lock.json`.

  The run ends with the doctor and replaces the README's "delete it and rerun to refresh" advice. `tests/fresh_install.sh` runs it after the rerun, with every release record set back, so each release is really fetched again. `DOTFILES_UPDATE=1` also works on a single stage, such as `DOTFILES_UPDATE=1 bash scripts/bootstrap_tools.sh`.

  The update leaves these alone and says so:
  - a tool found elsewhere on `PATH`, or as a link in `~/.local/bin` (pipx, uv and npm put links there; the bootstrap installs plain files);
  - a Neovim that the bootstrap did not link, and a font directory without the bootstrap's marker;
  - Homebrew pins, apt holds and winget pins (each installed package's pin is checked with `winget pin list` first);
  - tmux plugins pinned to a tag;
  - casks that update themselves (Ghostty);
  - on Windows, the running PowerShell 7 or Windows Terminal, and packages whose version winget cannot tell.

  A new Neovim, tree-sitter CLI or font must work before the one it replaces is gone: the Neovim tree has to run, the tree-sitter release is staged first, and the previous font directory waits hidden until fontconfig lists the family again. mise in `~/.local/bin` updates itself with `mise self-update`, which checks signatures and skips releases younger than a day, so a recorded latest tag would not always be the installed one. The oh-my-posh installer is given the tag, and zoxide's installs the latest, which is the tag just looked up. The doctor gained no check: the update ends with it, and the records only spare downloads. A machine installed before the records existed fetches every release tool once on its first update.

  **What a plain rerun already upgraded**, checked first as planned:
  - **Homebrew:** `brew install` upgrades an outdated formula unless `HOMEBREW_NO_INSTALL_UPGRADE` is set, against an index that `brew install` refreshes on its own at most daily. It never upgrades a cask, because the installer skips casks it finds in place.
  - **apt:** `apt-get install` upgrades the listed packages, but the eza and charm repository packages were skipped once present.
  - **winget:** nothing, because the installer skips every package `winget list` finds.

  **Found along the way:**
  - Two transient GitHub errors (500 and 502) stopped fresh-install runs, and the update looks up one tag per release tool, about 16 requests that a plain rerun never makes. Every curl call in the bootstrap (and the Homebrew installer download) now passes `--retry 5`, which retries timeouts and 408, 429, 500, 502, 503 and 504 answers. A unit test checks the flag on the lookup and the download.
  - `apt-get install -y` stops with "Held packages were changed" when a held package has an upgrade (exit 100, reproduced on Ubuntu 24.04). Plain installs had the same bug, so every `apt-get install` now leaves held packages out.
  - `brew upgrade` fails when it is named a pinned formula, so pins are filtered out first.
  - TPM's `update_plugins all` fails on catppuccin/tmux: `git pull` cannot work in its detached tag checkout. Pinned plugins are therefore not passed to it.
  - TPM updates plugins in background jobs, so a failed `git pull` never reaches its exit status. zinit's `update --all` returns 0 and only warns ("update returned N"). The update reads both outputs for those lines.
  - zinit pages its own changelog through `less` unless given `--no-pager`, so an update in a terminal could wait for a key.
  - A plain `winget pin add` only keeps a package out of `winget upgrade --all`; `winget upgrade --id` goes ahead regardless. Only blocking and gating pins answer with the "pinned" exit code.
  - Neovim's `require` searches 'runtimepath' before `package.path`, and on a machine with the configuration linked that includes the repository's own `config/nvim`. `tests/nvim_bootstrap_update.lua` (stubbed Mason and nvim-treesitter) therefore prepends the configuration under test.
  - A review pass found and fixed several problems before the PR:
    - an update could replace a working Neovim tree with a release that does not run;
    - binaries that pipx or uv linked into `~/.local/bin` counted as the bootstrap's;
    - TPM and zinit plugin failures passed silently;
    - a missing glow kept an installed gum from upgrading.
  - The first update on this Mac (2026-10-12) passed the doctor. It updated three zsh plugins and every tmux plugin but catppuccin, and found Homebrew, mise, the yazi flavors and every Neovim parser and server current. A second run after the review fixes changed nothing and passed again.
  - `DOCKER_DEFAULT_PLATFORM=linux/arm64` fresh installs of Debian 12 and Ubuntu 24.04 passed with every release record set back:
    - The update fetched 16 releases again on Debian 12 (no tree-sitter there, since glibc 2.36 is too old for it) and 17 on Ubuntu 24.04.
    - That covered the release binaries, the Neovim tree swap, the staged tree-sitter CLI, the font swap and both installer scripts.
    - mise's self-update and every Mason package and parser were already current.

- **Fresh-install CI** ([#9](https://github.com/Arthur-K-99/dotfiles/pull/9)). `tests/fresh_install.sh` installs the checkout in a new Debian or Ubuntu container as a user with sudo, with real downloads, reruns the installer, starts an interactive zsh on a pseudo-terminal, and loads tmux with its plugins (tmux-continuum, the last one, must have set its status hook), failing on any error they report. The terminal matters: without one, Debian 12's fzf 0.38 scripts print "can't change option: zle", which a real terminal never shows. The Fresh install workflow runs it on Debian 12 and 13 and Ubuntu 24.04 and 26.04 plus the macOS runner, on pull requests that touch the Unix install, weekly, and on demand. Its first runs found two bugs the mocked suite could not: a new Linux account has no `~/.local/bin`, which the oh-my-posh installer refuses, so the bootstrap stopped there on every distribution; and the tree-sitter CLI releases are built against glibc 2.39, so on Debian 12 (glibc 2.36) arm64 the bootstrap stopped before mise, the yazi flavors and the Neovim plugins, and x86_64, where 0.27.1 starts with a "weak version" warning, hung for ten minutes in Neovim's parser install in every run. The bootstrap now creates the directory, and a tree-sitter release the loader complains about ("GLIBC_x not found", fatal or weak) is left out and recorded with the glibc it failed on, so reruns fetch only a newer release and the doctor skips the CLI and the parsers (as on Windows without a compiler) only while that glibc is installed. A CLI that warns is replaced by the bootstrap and fails the doctor. (0.27.0 and 0.26.13 do not start on Debian 12 x86_64 at all.)
- **Linux font** ([#10](https://github.com/Arthur-K-99/dotfiles/pull/10)). The bootstrap installs CaskaydiaCove Nerd Font Mono from the latest Nerd Fonts release (`CascadiaCode.tar.xz`) into `~/.local/share/fonts/CaskaydiaCove` and runs `fc-cache`; the doctor asks fontconfig (`fc-list -q`) for the family, so a copy installed anywhere else counts. The new copy is assembled in a hidden sibling directory, which fontconfig ignores, so an interrupted copy never counts as installed, and a `CaskaydiaCove` directory without the bootstrap's marker file is left alone. Only the Mono family is kept, 33 MB of the 100 MB the archive unpacks to: Ghostty and the Windows Terminal fragment select it, and macOS and Windows install the whole family only because their installers do. `fontconfig` and `xz-utils` join the apt list. WSL skips the font, since Windows Terminal renders WSL with the Windows font. `oh-my-posh font install`, which Windows uses, was tried first: it works without a terminal but floods a log with progress frames and installs into `/usr/share/fonts` as root.

## Known issues

Observed and not fully explained, or caused upstream; kept so they are recognised when they come back.

- **Debian 12 x86_64 parser installs hang** with tree-sitter 0.27.1, which starts there with a "weak version `GLIBC_2.39'" warning. Every parser compiled, then one install step (PowerShell in CI, another parser in emulated runs) did not finish until nvim-treesitter's ten-minute wait timed out, in 3 of 3 runs and never on Debian 13 or Ubuntu. Building the same parser with that binary alone took a second, so the hang is inside nvim-treesitter's asynchronous install; the root cause is unknown. #9 leaves such a CLI out, so Debian 12 has no compiled parsers. Reruns try every new tree-sitter release, so a build that runs cleanly on glibc 2.36 brings them back without a change here.
- **`tar: Write error` on the macOS runner** in `test_theme_switch_round_trip`, once; the other run of the same commit passed. The fixture now copies with `cp -R`. Cause unknown.
- **zsh-you-should-use prints `tput: No value for $TERM`** five times when zsh starts without `TERM` (cron, some IDE tasks, Claude Code's shell). Upstream and harmless.
- **Debian 12's fzf 0.38 prints `can't change option: zle`** when its zsh scripts load without a terminal. A real terminal never shows it; `tests/fresh_install.sh` runs zsh under util-linux `script` for this reason.
- **Docker on a Windows host counts as WSL**, since containers share the WSL2 kernel, so `tests/fresh_install.sh` run there skips the font.
- **This Mac's oh-my-posh was stale and invisible to Homebrew** (2026-10-12, fixed 2026-10-14, [#22](https://github.com/Arthur-K-99/dotfiles/pull/22)):
  - It ran 26.19.1 from a plain file in `/opt/homebrew/bin`, not from the bootstrap and not linked by Homebrew.
  - That file shadowed an unlinked 28.4.0 keg from the `jandedobbeleer/oh-my-posh` tap. Homebrew 7 refuses to load that tap ("Refusing to load ... from untrusted tap"), although `brew update` still updates it, so neither `brew outdated` nor the update saw the keg. The update reported oh-my-posh as not installed by the bootstrap and left it alone.
  - Cleaned by hand on 2026-10-14 (Homebrew 7.0.9) with the steps in `docs/troubleshooting.md`; `scripts/update.sh` then installed 31.8.0 into `~/.local/bin` and the doctor passed (118 checks). Plain `brew uninstall oh-my-posh` stopped at the same refusal, and so did `brew untap` while the keg was installed; `--formula` and `--force` were only tried together.
- **Homebrew 7 warns about untrusted taps during some updates** (7.0.9, 2026-10-14, [#22](https://github.com/Arthur-K-99/dotfiles/pull/22)): `brew upgrade` in `scripts/update.sh`, which runs only when a declared formula is outdated, prints `Warning: The following taps are not trusted:` for any tap the user added whose formulae are installed, such as `hashicorp/tap` (terraform) on this Mac, and Homebrew ignores that tap's formulae. The dotfiles use no tap; `docs/troubleshooting.md` explains the message.
- **GitHub answers with HTTP 500 or 502 now and then.** On 2026-10-12, within half an hour, the yazi asset download failed with a 500 in a Debian 12 fresh install, and the zoxide `releases/latest` lookup failed with a 502 in an Ubuntu 24.04 update. Both URLs worked minutes later. The yazi asset then failed four times in a row in an Ubuntu 24.04 install with `--retry 3` (1, 2 and 4 seconds apart). Every curl call in the bootstrap then passed `--retry 5`, about 30 seconds of backoff, and in the next Debian 12 run a 503 and four 502s in a row came and went without failing it. On 2026-10-14 lazygit's asset answered 500 six times over those 30 seconds in a Debian 12 run on CI, so the bootstrap now passes `--retry 7`, about two minutes. macOS's `/usr/bin/curl` 8.7.1 retried an HTTP/1.1 503 but not an HTTP/2 one: with `-f` it exits 56 at once. `dotfiles_curl` passes `--fail-with-body` instead, which exits 22 and is retried (see "Bounded downloads" in Done).
- **OrbStack's Docker engine hung** on this Mac (2026-10-13) during the keyring experiments: even `_ping` on its socket timed out while `orb status` said Running, with an OrbStack update pending. `orb restart docker` hung too; `orb stop` then `orb start` brought it back. If `tests/fresh_install.sh` or a container check hangs, check the socket first. It hung again on 2026-10-14 with two fresh installs running side by side: `_ping` timed out, and both installs failed with nvim-treesitter's ten-minute install timeout (`async.lua:158: timeout`) while compiling parsers. The engine recovered without a restart, and both images passed when run again one at a time. A parser timeout in a local run is therefore worth checking against the engine first.
- **Which Ghostty file wins on macOS is unchecked** (Ghostty 1.3.1). The managed config loads `~/.config/ghostty/local` through `config-file = ?local`, and macOS Ghostty also reads `~/Library/Application Support/com.mitchellh.ghostty/config`. The README said the latter loads after both. Ghostty's documentation says `config-file` includes take effect only after the entire configuration is loaded, which would make `local` win instead. An experiment with a scratch `HOME` was inconclusive, since Ghostty did not read an Application Support file from it, so `docs/tools.md` only says to keep a setting in one of the two.
- **gpg starts an agent even for `--show-keys` and `--import`** (seen with gpg 2.2.40 and 2.4.7). The scripts stop it with `gpgconf --kill all`; in a container without an init, the stopped agents stay as zombies, which a machine's init reaps.
- **winget 1.11 cannot find Carapace by its exact id** (`rsteube.Carapace`, a portable zip winget installed itself): `winget list --id ... --exact` and `winget upgrade --id` miss it while `winget list --id` without `--exact` lists it. The Windows install works around it (see "A fresh install on Windows"); a manifest or winget fix upstream would make the workaround unnecessary.
- **oh-my-posh could not be started at the font step of the Windows fresh install,** once (2026-10-14, [run 38615827813, attempt 1](https://github.com/Arthur-K-99/dotfiles/actions/runs/38615827813/attempts/1)); the second attempt passed. See "oh-my-posh on Windows from its release".
- **Windows PowerShell transcripts record caught errors:** each `Get-Item` miss that `Get-DotfilesPathItem` catches shows up as `TerminatingError(Get-Item)` in a transcript, about two lines per managed file on a first install. They never reach the console.
- **PowerShell starts slowly with the profile on the CI runner:** 7 to 14 seconds per start in both editions (14.0, 10.1, 9.0 and 7.7 s in the passing run), against 0 to 2 without oh-my-posh's init, which takes nearly all of it. Nothing in the job fails on it. Whether a desktop sees the same (the MSIX activation, a cold cache) is unknown.

## Ideas parked

Considered and not scheduled, kept so they are not rediscovered.

- zellij as a tmux alternative: no Windows build, and the tmux investment is already large.
- Starship as a prompt: oh-my-posh already serves zsh and PowerShell from one file.
- zinit turbo mode: plugins cost about 25 ms in total after phase 1, so deferred loading buys little and adds ordering surprises.
- chezmoi or another dotfiles manager: the custom linker, doctor and tests cover the needs so far.
- inshellisense: a pty wrapper that fights the zsh plugins and tmux; carapace covers completion and can bridge its specs if needed.
- pay-respects: no Homebrew core, apt or winget package and an installer that edits shell files. Revisit when one package manager carries it.
- tokei: upstream has shipped no binaries since 12.1.2, so Linux would need cargo. `cargo install tokei` by hand if wanted.
- Pulling the repository from the update: `scripts/update.sh` would have to settle local changes and diverged branches, and which commit a machine runs is a decision to make by hand. `git pull`, then update.
- The API's `Date` header as the clock for the release age, instead of the machine's. A clock behind makes releases look young (older ones are taken, and a tool not installed yet stops the run with a hint only when none of the 30 most recent qualifies) and one ahead shortens the delay, but mise, pnpm, npm and uv all use the local clock, and the header would need parsing of its own.
- Parsing each tool's `--version` to decide on updates: every tool formats it differently, and recorded release tags answer the same question without running anything.
