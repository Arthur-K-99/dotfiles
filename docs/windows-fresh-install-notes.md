# Windows fresh install: notes from the first runs

Working notes from the branch `rice/windows-fresh-install` (2026-10-14), to fold into `docs/roadmap.md`. Until this branch nobody had run `install.ps1` or `scripts/update.ps1` on a clean machine; only the mocked suite covered them. The branch starts at eb7b82e and does not contain later `main` commits (such as b00eec4's quieter Neovim bootstrap).

## What was added

- **`tests/fresh_install.ps1`**, the Windows side of `bash tests/fresh_install.sh --here`, in stages (`-Stage Prepare|Install|Rerun|Update|Doctor|Shells|Collect`, default `All`). Each stage starts its shells with PATH read from the Machine and User registry values, as a reopened terminal has it, from a script file under the log directory (`$env:RUNNER_TEMP\fresh-install` on a runner) with a transcript beside it. It changes the machine beyond the install, so it is for disposable machines only.
  - **Prepare** records the runner (Windows, execution policies, `winget --info`, the App Installer, Terminal and XAML packages, which doctor commands exist already), installs the newest version but one of fzf and of Carapace, and writes a placeholder profile for both PowerShell editions.
  - **Install** runs `Set-ExecutionPolicy RemoteSigned -Scope CurrentUser -Force` and `install.ps1` from Windows PowerShell, as the README says, and checks that the older packages were kept and that each placeholder profile was backed up once (with its content) and replaced by the managed profile.
  - **Rerun** runs `install.ps1` from a Windows PowerShell that loads the new profile and fails if the transcript shows anything installed, upgraded, linked, copied, backed up or created.
  - **Update** pins sd (`winget pin add --id chmln.sd --exact`), runs `scripts/update.ps1` from `pwsh -NoProfile`, and checks that the update upgraded both older packages (winget then lists a newer version and none available), left the pinned sd and the running PowerShell 7 alone, and ended with the doctor.
  - **Doctor** runs `scripts/doctor.ps1` in a new Windows PowerShell and a new PowerShell 7.
  - **Shells**: both editions start with the managed profile, and again with PSReadLine imported before it, with nothing on stderr, stdin closed and a time limit; a probe checks that `ls`, `cat` and `vim` are eza, bat and nvim, that `la`, `ll`, `tree`, `y` and zoxide's `__zoxide_z` exist, that oh-my-posh (`oh-my-posh-core` module) and mise (`MISE_SHELL`) are initialised and, with PSReadLine, its options and Tab binding. Each start's duration is printed. Neovim headless loads every parser `require('dotfiles.tools').parsers` lists through `vim.treesitter.language.add`, and the Windows Terminal fragment parses as JSON. A command that times out, or exits while processes it started hold its output open, fails with those processes listed.
  - **Collect** copies winget's DiagOutputDir, `winget --info` and Neovim's and Mason's logs into the log directory.
- **`.github/workflows/fresh-install-windows.yml`** ("Fresh install (Windows)"): one step per stage on `windows-2025`, `timeout-minutes: 90` with per-step limits, `GITHUB_TOKEN` from `github.token`, default shell `powershell -NoLogo -NoProfile -NonInteractive -Command ". '{0}'"` so no step loads the profile the install puts in place, and an `if: always()` upload of the log directory as the `fresh-install-windows` artifact. Triggers: pull requests touching `**/*.ps1`, `packages/winget.txt`, `config/**` or the workflow; weekly (`43 4 * * 1`); on demand. `fresh-install.yml` still ignores `**/*.ps1` and now also the Windows workflow file.

## Findings and fixes

1. **The Nerd Font install hit GitHub's API limit.** `oh-my-posh font install CascadiaCode` resolves the font name through `api.github.com/repos/ryanoasis/nerd-fonts/releases/latest` (and `microsoft/cascadia-code`) without a token (oh-my-posh 31.8.0, `src/cli/font/fonts.go`; it ignores `GITHUB_TOKEN`), and on the shared runner address got refused: exit 70, "failed to get ryanoasis/nerd-fonts release". Fixed: `Invoke-DotfilesFontInstall` passes `https://github.com/ryanoasis/nerd-fonts/releases/latest/download/CascadiaCode.zip`, which oh-my-posh accepts as a URL and downloads without an API request (6636cc7). This matters at home too: the API allows 60 anonymous requests an hour per address.
2. **oh-my-posh is an MSIX package now; its font install works.** winget's `JanDeDobbeleer.OhMyPosh` 31.8.0 is `InstallerType: appx` (family `ohmyposh.cli_96v55e8n804z4`, restricted capabilities `runFullTrust` and `unvirtualizedResources`); the command is the alias `%LOCALAPPDATA%\Microsoft\WindowsApps\oh-my-posh.exe`. Run from the package, `font install <zip URL>` exits 0 in about 20 s and installs per user outside the package: the files in `%LOCALAPPDATA%\Microsoft\Windows\Fonts`, their names under `HKCU\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Fonts` (CaskaydiaCove NF, NFM and NFP), which `Test-DotfilesNerdFont` reads. Only oh-my-posh's own caches land in the package's `LocalCache`. See Left open for the prompt.
3. **winget 1.11 cannot find Carapace by its exact id.** The first rerun installed `rsteube.Carapace` again. On winget 1.11.510 the portable zip that winget itself installed is missing from `winget list --id rsteube.Carapace --exact` (and with `--source winget`), while `winget list --id rsteube.Carapace` lists it under that id, with the available version. The verbose log shows the exact search looking the installed package up by normalized name and publisher across the manifest's per-architecture names (`carapace`, `carapace(x86)`, ...; only the x86 and arm64 installers carry `AppsAndFeaturesEntries`) and finding none. `winget upgrade --id rsteube.Carapace`, with or without `--exact`, answers "No installed package found" (0x8A150014) even with 1.0.6 installed and 1.8.0 available; `winget install --id rsteube.Carapace --exact` over 1.0.6 replaces it with 1.8.0 (exit 0); `winget pin add/list/remove --id rsteube.Carapace --exact` work. Every other package in `packages/winget.txt` is found with `--exact`. Fixed (09bd66d): a package the exact listing misses counts as installed when the listing without `--exact` has a row naming its id (`Get-DotfilesWingetListedVersions`, which finds the row by the id alone because winget localizes the headers); the update reads that row and installs the package again when it shows an available version, reporting `upgraded: <id> (installed again: winget upgrade cannot find it)`, otherwise `up to date`. The harness seeds an older Carapace so the update takes that path for real (e9b0195): 1.0.6 to 1.8.0, with fzf 0.74.3 to 0.74.4 through `winget upgrade`.
4. **direnv's PowerShell hook failed at every start.** Every PowerShell start printed `direnv: error couldn't find a configuration directory for direnv`, then `Invoke-Expression` failed on the empty hook. direnv (2.38) finds its configuration, cache and data directories through `XDG_*_HOME` or `HOME`, which Windows does not set, and looks for bash before printing anything (Git for Windows does not put its bash on PATH by default; a `bash` on PATH may be WSL's launcher). Its hook also throws on purpose below PowerShell 7.2 and uses `LocationChangedAction`. And `Invoke-Expression "$(direnv hook pwsh)"` joined the hook's lines with spaces. Fixed (49f3329): the profile runs the hook only in PowerShell 7.2+, sets `HOME` to `$HOME` when unset, points `DIRENV_BASH` at `%ProgramFiles%\Git\bin\bash.exe` when it exists, and pipes the hook through `Out-String`. The mocked test never saw this because its direnv is a stub.
5. **PowerShell 7 never exited after a non-interactive command that loaded the profile.** `pwsh -File`/`-Command` without `-NoProfile` hung forever after its command finished (the Shells stage ran into its 10-minute limit). `dotnet-stack` on the hung process: the host's main thread waits in `ConsoleHost.DoRunspaceInitialization` → `ExecuteCommandAsyncHelper`, while the pipeline thread is in `RaisePipelineStateEvents` → `Runspace.OnAvailabilityChanged` → CompletionPredictor's `SyncRunspaceState` → `PowerShell.Invoke()`, a nested pipeline on the busy runspace: a deadlock. The chain: the config's `transient_prompt` makes oh-my-posh's init set PSReadLine key handlers, which imports PSReadLine even in a non-interactive shell; the profile's PSReadLine block assumed only the console host loads it (for an interactive shell) and so imported CompletionPredictor. Without oh-my-posh, with the profile dot-sourced from a `-NoProfile` script instead of loaded at startup, or in Windows PowerShell (no CompletionPredictor), it exits. Fixed (057ed2d): the profile reads whether PSReadLine is loaded before anything else runs and gates the PSReadLine block on that; the mocked test's oh-my-posh stub imports PSReadLine like the real one, and the test fails with the old condition. Any tool that runs `pwsh -Command` with the profile (editor tasks, hooks) would have hung on a machine with this setup.
6. **Restart to finish.** The install stopped on winget's 0x8A150109 (restart to finish) as a failure while the update counted it as an upgrade. No package returned it on the runner; the install now reports `installed: <id> (restart Windows to finish)` and carries on, and the doctor at the end finds out whether the package already works (737efb2).
7. **git's detached-HEAD advice.** Run 38554393890's install transcript holds five copies of git's 14-line detached-HEAD advice from `plugins()`. A Windows-side fix (`GIT_CONFIG_*` around the nvim call, 9dcab4d) was reverted (d3e2d5a) at the coordinator's request: the setting moves into `config/nvim/lua/dotfiles/bootstrap.lua` (`M.plugins()` sets the variables through `vim.env`), which covers Windows too. Noted while doing it: on macOS, `[Environment]::SetEnvironmentVariable($name, $null)` from PowerShell left an empty variable rather than removing it, so restoring an unset variable needs `Remove-Item Env:<name>`.
8. **Expected failures that did not occur:** msstore errors on `winget list` (none on this image); Windows Terminal's MSIX on Server (inbox and upgradable); the doctor in a new process (it passes once PATH comes from the registry, which is what reopening the terminal does; a terminal opened before the install still lacks the new PATH entries, as the README's "reopen" advice says); Mason's npm installs and the MSVC parser builds near their timeouts (about 3.5 and 2 minutes against 10-minute waits).

## Left open

- **oh-my-posh's MSIX package and PowerShell 7's prompt.** In one probe (oh-my-posh installed by winget in the same step, then `oh-my-posh init pwsh` from the checkout directory), the init's `Invoke-Utf8Posh` failed: `[Diagnostics.Process]::Start()` of `$global:_ompExecutable`, which the MSIX build sets to the bare `oh-my-posh.exe`, threw "An error occurred trying to start process 'oh-my-posh.exe' ... The file cannot be accessed by the system." PowerShell's `&` starts the same alias fine. In the full fresh install it did not happen. Upstream this is [JanDeDobbeleer/oh-my-posh#7833](https://github.com/JanDeDobbeleer/oh-my-posh/issues/7833) (closed after 30.8.1, reported again for 31.3.0 and 31.5.0, last on 2026-10-13; the maintainer cannot reproduce it; reporters see the App Installer window open on every prompt and say a full WindowsApps path does not help). If it reaches a real machine, the remedy would be installing oh-my-posh on Windows from its release (`posh-windows-amd64.exe`/`-arm64.exe`, each with a `digest`, release immutable) into `~/.local/bin` as on Unix, instead of the winget MSIX. That is a decision, not done here.
- **PowerShell starts slowly with the profile on the runner,** because of oh-my-posh's init: about 7 to 10 s per start in every probe, in both editions, against 0 to 2 s without it. In the passing run the Shells stage measured pwsh 14.0 s, pwsh with PSReadLine 10.1 s, Windows PowerShell 9.0 s and 7.7 s. It is not yet known whether a desktop sees the same (MSIX activation, a cold cache) or only the runner; nothing in the job fails on it.
- **Upstream reports worth filing:** the Carapace manifest/winget correlation (winget-pkgs or winget-cli), CompletionPredictor's deadlock in a non-interactive host that loaded PSReadLine late (PowerShell/CompletionPredictor), oh-my-posh importing PSReadLine in non-interactive shells for its key handlers.
- **Transcript noise:** Windows PowerShell transcripts record each `Get-Item` miss that `Get-DotfilesPathItem` catches as `TerminatingError(Get-Item)`, about two lines per managed file on a first install. They never reach the console.
- **The Nerd Font is still unverified.** The URL change only removes oh-my-posh's API lookups; the archive is still taken from `latest/download` without a digest check or a recorded release (the roadmap item "The Nerd Font on Windows: updates and verification" stands).
- **README and roadmap text to update:** direnv in PowerShell now needs PowerShell 7.2 (the README's tool table says "Yes" for native Windows without that); the profile sets `HOME` when it is unset and `DIRENV_BASH` to Git's bash; the PSReadLine setup (keys, colors, predictions, carapace, atuin, PSFzf) runs only in interactive shells; the Fresh install section can mention the Windows job; the roadmap item "A fresh install on Windows" can move to Done with the facts above (winget exit codes and the pin table were seen on a machine: 0x8A15002B, 0x8A150014, the `Pinning` row).
